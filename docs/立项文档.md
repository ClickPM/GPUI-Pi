## 一、项目定位与边界

用 GPUI + gpui-component 写一个 **pi 编程智能体的原生桌面客户端**，1:1 复刻 pi-web 0.8.9 的能力，不使用 Electron、不打包 Node/Python/DeepSeek Harness。

这是**新仓库、新项目**，不是 pi-web-desktop 的重写分支。两者并行存在、共用 `~/.pi/agent/`：

| | pi-web-desktop（保留） | GPUI-Pi（本项目） |
|---|---|---|
| 定位 | 兜底 + DeepSeek Harness 入口 + 扩展/技能部署 | 日常 pi 客户端 |
| 演进 | 冻结在 `claude/dsh-integration` 状态，不再加 pi 侧功能 | 主线 |
| 卸载条件 | GPUI-Pi 达到 1:1 且稳定运行 1 个月后再议 | — |

### 明确不做（v1）

| 不做 | 理由 |
|---|---|
| 内置 Python | 体积（340MB）；连带 `ppt-master`、`wiki-*`、`okf-visualizer` **全部移出 v1 范围** |
| 内置技能部署（`skills-seed`） | 技能住在 `~/.pi/agent/skills/`，由 pi-web-desktop 负责铺；GPUI-Pi 只消费不部署 |
| DeepSeek Harness 第二运行时 | 留在 pi-web-desktop |
| Mermaid 渲染 | 源码直出为代码块。**连带收益：不需要 WebView，不依赖 WebView2 Runtime** |
| PWA / 移动端布局 / 浏览器远程访问（`web-auth`） | 原生壳天然不具备，且当前 Electron 版也只绑 127.0.0.1 |
| 多标签页 / 浏览器通知 | 用原生窗口与系统通知替代 |
| 内置 Node / npm | 内核换官方独立二进制，无 npm 安装行为 |

### v1 完成的定义（DoD）

1. 附录 A 的 1:1 对照表全绿（标 `OUT` 的除外）；
2. Windows x64 安装包 ≤ 220MB，空机器双击可用（除模型 API Key 外零配置）；
3. 连续 7 天作为主力客户端使用无阻断性缺陷。

## 二、上游钉版本与解冻策略

v1 开发期间**锁死**，不追上游。

| 上游 | 钉死值 | 角色 |
|---|---|---|
| `agegr/pi-web` | `v0.8.9` / `2a6e53710f6409e0cceb3de839a62f8cdf3ca3ca` (2026-08-15) | **功能对照基线**，只读源码，不作运行时依赖；固定在 `vendor/upstream/pi-web-0.8.9/` |
| `earendil-works/pi` | `v0.84.2` / `914cf1472e715297caa30db4b9535d534a9eb718` | 运行时内核用官方独立二进制；源码参考固定在 `vendor/upstream/pi-0.84.2/` |
| `longbridge/gpui-component` | `000114aa` (2026-08-15) | UI 组件库 |
| `zed-industries/zed`（gpui / gpui_platform） | `cc053a4a` | 与上面那版 gpui-component 的 `Cargo.lock` 一致 |

**R21 内部 crate 的 Cargo.lock 口径**：R21 新增仓库内部 path crate `pi-runtime`。`Cargo.lock` 仅允许增加 `pi-runtime` 的本地 package 记录（只列实际使用的既有 workspace 依赖），以及 `gpui-pi` 对该 path crate 的依赖边；禁止任何上游 package 的 version / source / checksum 漂移。本轮不得执行 `cargo update`，并须用 `check-pins.ps1` 与 lock diff 核对该例外之外没有变化。

**为什么必须钉**：近 60 天上游 `pi-web` 398 commit、`pi` 内核 1108 commit。移动靶做不了 1:1；GPUI 自身 pre-1.0，跟 main 分支会被 breaking change 打断节奏。

**解冻策略**（v1 交付之后，不在本文档范围内执行）：
- 先解 `pi` 内核（只有 RPC 协议这一个接触面，风险最小），跑通全部 T2 集成测试再合；
- 再解 gpui / gpui-component（一次一个，看 CHANGELOG 逐条评估）；
- `pi-web` 基线最后解 —— 它只是对照物，解冻等于"接受新的复刻目标"，应作为 v2 立项决策而非日常维护。
- 解冻时 diff 是**积压量不是增量**，预留独立的一轮工作，不要塞进功能轮次。

## 三、目标架构

```
       ┌───────────────┐        ┌───────────────┐
       │  crates/app   │        │   crates/ui   │      ← 依赖 GPUI
       └───────┬───────┘        └───────┬───────┘
               │ SessionHandle          │ ConversationDocument
               │ Snapshot / Dirty       │ （渲染中间模型）
       ┌───────▼───────────┐            │
       │ crates/pi-runtime │            │                ← 纯逻辑
       └───┬───────────┬───┘            │
           │           │                │
┌──────────▼────┐ ┌────▼─────────┐ ┌────▼───────────────┐
│ crates/pi-rpc │ │crates/pi-data│◄┤  crates/pi-render  │  ← 纯逻辑
└───────┬───────┘ └──────┬───────┘ └────────────────────┘
        │                │
        │ JSONL/stdio    │ 直接读写文件
        ▼                ▼
  vendor/pi/pi.exe  ~/.pi/agent/
  (--mode rpc)      sessions/ models.json settings.json
```

> `pi-render` 是 **app / ui 与 pi-runtime 共享的类型层**，不是 `pi-runtime` 的下游：`pi-runtime` 用它在 Runtime 内就地归并流式事件，`app` / `ui` 用它渲染 `ConversationDocument`。`crates/ui` 对 `pi-render` 的直接依赖必须保留，不得为了"分层好看"改成经 `pi-runtime` 中转。

### crate 划分（关键设计决策）

| crate | 依赖 GPUI | 职责 |
|---|---|---|
| `pi-rpc` | ❌ | 单个 Pi RPC 子进程生命周期、JSONL 分帧、命令/事件 serde、请求-响应 id 关联、崩溃重启与进程树终止。**自动重启策略由上层配置**，见「会话与进程模型」的重启决策权条款 |
| `pi-data` | ❌ | `~/.pi/agent/` 文件层：会话 JSONL 解析、`models.json`、`settings.json`、扩展/技能目录扫描、项目分组 |
| `pi-render` | ❌ | 消息 → 可渲染中间模型：Markdown 分块、ANSI 解析、diff 解析、工具调用卡片归类 |
| `pi-runtime` | ❌ | 应用级 `RuntimeManager`：所有内建 `pi --mode rpc` Runtime 的唯一生产创建入口；Actor、Snapshot、调度、背压、资源预算与子代理任务 |
| `ui` | ✅ | 基于 gpui-component 的应用级组件封装 |
| `app` | ✅ | 窗口、面板布局、轻量状态投影与入口；不直接拥有 `pi_rpc::Client` |

> **四个纯逻辑 crate 不依赖 GPUI**：它们无需窗口、无需 GPU 即可完整单测。`pi-rpc` 继续只负责“一 Client、一受监督进程”，跨 Session 的并发、回收和内存预算只放在 `pi-runtime`，不在两个 crate 间重复实现 supervisor。

### 会话与进程模型

- **一个 Resident Runtime = 一个 `pi --mode rpc` 子进程**（立项实测常驻约 203MB）。这是相对 pi-web 的**内存回归**：pi-web 是单 Node 进程内 `Map<sessionId, AgentSessionWrapper>` 挂 N 个会话，而钉死的 RPC 协议里一个进程同时只绑定一个会话（`switch_session` 是切换而非并挂）。多会话在本架构里天然昂贵，有界运行时正是为此存在。
- Session 可以长期存在，但不保证永久拥有进程：`Parked` Session 只保留轻量摘要与 session file，需要运行时再受控恢复。
- `RuntimeManager` 是应用进程级共享服务，跨窗口、Workspace、用户 Session、内建子代理和 maintenance job 共用总预算。`ChatPanel` 只持轻量 `SessionHandle`；关闭或切换 UI 绑定不直接决定进程生命周期。
- 所有 GPUI-Pi 自身创建的用户 Session、内建子代理和 maintenance `pi --mode rpc`（包括历史 HTML 导出）必须经 `RuntimeManager`；`app` 生产代码不得直接调用 `Client::spawn`。`pi-rpc` 自身的隔离测试仍可直接创建 `Client`。
- **Maintenance job 不占用户会话运行槽**：历史 HTML 导出这类短生命周期、`--offline --no-extensions` 的 Runtime 使用独立的小配额（初值：并发 1），只计入内存预算。否则两个用户会话跑满时导不出 HTML，属于用有界化换掉了既有功能。

**重启决策权（R21 必须定死）**

`pi-rpc` 的 supervisor 目前自带自动重启：进程非正常退出且未置 `shutdown` 标志时，在 `restart_window` 内最多重启 `max_restarts` 次，并从 `resume_session` 恢复。它与 `RuntimeManager` 的 `Failed → Queued → Starting` 状态机是**两套恢复机制**，若不定归属，Manager 判为 `Failed` 并释放运行槽后，底层可能已经把 pi 拉起来，「活跃 Pi 进程不超过配置上限」这条验收会在崩溃恢复路径上概率性失效。

- 默认口径：**Manager 拥有重启决策权** —— 经 `RuntimeManager` 创建的 Runtime 一律把 `max_restarts` 设为 0，恢复走 Manager 状态机；
- 若某场景确需保留底层自动重启，Manager 必须订阅 `LifecycleEvent::Restarting / Restarted`，把这次重启计入运行槽与内存预算，禁止让它绕过调度器；
- 反过来，这套「优雅 shutdown + 从 session file 恢复」是 Park/Resume 的现成实现，R23 应复用而不是重写。

**Park / Resume 优先复用 `switch_session`，而不是 kill + 冷启动**

`switch_session` 已实现并在用（含"主命令成功但元数据校准失败"的处理）。因此 `IdleWarm` Runtime 应设计成**可复用进程池**：唤醒一个 Parked Session 时优先让空闲 Runtime `switch_session` 接管，恢复成本从「重起一个约 203MB 的进程」降到一次 RPC 往返；只有无空闲 Runtime 时才冷启动。`Warm Idle` 的语义因此是"可被任意 Session 复用的热进程"，不是"某个 Session 的预热副本"。

**两类子代理，边界必须分清**

| | Manager 派发的子代理（R26/R27） | pi 内核 / extension 自行 spawn 的子代理 |
|---|---|---|
| 进程归属 | `RuntimeManager` 直接创建 | Runtime 的**子进程**（官方 `subagent` 示例扩展对每次调用 spawn 一个 `pi --mode json -p --no-session`，且支持 `tasks` 数组并行） |
| 并发/深度配额 | 受 Scheduler 管控 | **不受管控** —— 用户一句"并行审查这三个模块"即可绕过 |
| 会话文件 | 有（见下条 `parentSession`），可 Park/Resume、可回看 | 官方示例扩展用 `--no-session`，无会话文件 |
| 内存与清理 | 完全纳管 | 在同一进程树/Job Object 内，**可被 R25 的进程数与内存硬限制兜底**，也随 Runtime 关闭一并清理 |

- 因此 R26 的并发验收只对 **Manager 派发的子代理**成立，文档与任务卡不得表述为"所有子代理"；
- 同时，不得把第三方 extension 进程一概说成"无法强制控制"——它们在进程树内，Job Object 的 active-process / memory hard limit 对它们有效，这正是 R25 相对 `taskkill /T` 的核心增量。仍然无法做到的是**按任务语义限流**（Manager 看不见 extension 内部的任务边界）；
- R26/R27 相对官方 `subagent` 扩展的增量价值必须成立且写明：**有会话文件（可恢复、可回看）、有进度与结果 UI、mutating 任务有 worktree 隔离**。若这三点都不做，就不该自建第二套子代理。
- Manager 派发的子代理会话必须使用钉死协议已有的 `new_session { parentSession }`，把父子关系落进 pi 的会话文件，而不是只存在于 Manager 的内存里——否则应用崩溃重启后父子关联即丢失。

**其余约束**

- Provider 登录、模型配置等一次性非 RPC CLI 不属于 Session Runtime。
- Runtime 使用 Manager 分配的稳定 `RuntimeId`；Pi 的 `session_id` 可在 fresh 启动后校准更新，不作为 Handle 的不可变主键。每个 Runtime 独立维护进程 `epoch` 与 Snapshot `revision`，UI 是否当前可见不参与 stale-event 判定。
- 默认并发数、队列长度、Warm 数量、Idle TTL 与内存水位均为**可配置初始值**，须根据 Windows 实测调整，不构成不可变产品契约。
- R21 只完成集中化，使用 `single_session_compat` 策略保持现有“切换会话时优雅停止旧 Runtime”的外部行为；R22 先完成有界 Actor 与事件背压，R23–R24 才开放 Park/Resume 和多会话并行，禁止先把当前无界路径按 Runtime 数量放大。

### 缺口⑤ 展开：GPUI 的 Windows 端是官方支持，不是社区支持

这条容易踩错判断，所以把核查结果留档。**证据取自我们钉死的那个 commit（`cc053a4a`）的源码本身**，不是二手说法。

| 核查项 | 结论 |
|---|---|
| crate 归属 | `crates/gpui_windows` 是 zed monorepo 的 in-tree 一等 crate，**12,120 行**，与 `gpui_linux`（15,070）、`gpui_macos`（12,503）同量级，不是薄适配层 |
| 官方 CI | `.github/workflows/run_tests.yml` 有 `clippy_windows` 与 `run_tests_windows`，跑在自建 32 vCPU Windows runner（`self-32vcpu-windows-2022`），且二者都在最终门禁 job 的 `needs` 里 —— 与 linux/mac 并列必过 |
| 发版流水线 | `release.yml` / `release_nightly.yml` / `run_bundling.yml` 均含 windows |
| gpui README | Windows 列为三平台之一：「no features are required. Windowing uses Win32 and text uses DirectWrite」 |
| 官方文档 | `zed.dev/docs/windows` 提供 stable 下载与 winget 安装，无 experimental / community / preview 字样；`docs/src/development/windows.md` 是正式构建指南 |

**历史来源**：2024–2025 年 Windows 端长期是「社区推动 + 官方不发包、只能自源码编译」，转折点是 Zed 1.0（发布页记 2026-04-29）三平台齐发。旧印象已过期。

**所以风险不在"非官方"，而在这三条**：

1. GPUI 自身 pre-1.0，README 明写 frequent breaking changes —— 已用提交进仓库的 `Cargo.lock` 对冲；
2. Windows 后端更年轻，新特性通常 macOS/Linux 先落地；
3. **IME 走 IMM32 而非 TSF**。钉死 commit 里的实现是完整的 —— `WM_IME_STARTCOMPOSITION` / `WM_IME_COMPOSITION` 消息处理、`ImmSetCompositionWindow` + `ImmSetCandidateWindow`（候选窗定位）、`ImmAssociateContextEx`（启停）、`ImmNotifyIME(NI_COMPOSITIONSTR, CPS_COMPLETE)`（提交组合串）—— 但 IMM32 路线在部分输入法上存在已知边角。

结论：**风险定性从「可能不成熟」修正为「实现完整，但 IMM32 路线需实测验证」。R1 门禁第 1 条照测不误**，不因为"官方支持"而放宽。

## 六、开发模式：`/loop` 强制规范

### 轮次任务卡

每轮建立独立目录 `rounds/round-NN/`，任务卡固定为 `rounds/round-NN/round-NN.md`；该轮的实测记录、阻塞报告、复盘等管理产出也放在此目录。`rounds/` 根目录只保留 `README.md`、`TEMPLATE.md`、`BACKLOG.md`。源码、脚本、fixture 与构建产物仍放标准工程目录，不复制进轮次目录。

任务卡结构固定：

```markdown
# Round NN — <标题>
## 目标            一句话，可证伪
## 前置            依赖哪些轮次已完成
## 交付物          文件级清单
## 验收            可执行命令 + 期望结果（T1/T2/T3 分级）
## 禁止            本轮明确不许碰的东西（防范围蔓延）
## 失败处理        连续 2 次 validation 不过 → 停下写 BLOCKED.md 并呼人
```

### loop 契约

1. **一轮 = 一个 `/loop` 任务**，允许内部多次迭代，直到 `scripts/validate.*` 全绿；
2. 每次迭代结束**必须**跑 validation，不许"看起来对了就下一步"；
3. 全绿后：一个 commit（message 说明 why）+ 更新 `ROUNDS.md` 进度表 + 在任务卡尾部追加 `## 本轮实测` 段落（数字、踩坑、偏离设计的地方）；
4. **禁止跨轮次改动**。发现前面轮次有问题 → 记进 `rounds/BACKLOG.md`，不当场改；
5. 连续 2 次 validation 失败 → 写 `rounds/round-NN/BLOCKED.md` 停下呼人，不许放宽验收标准自我通过。

### 验收分级

| 级别 | 含义 | 谁执行 |
|---|---|---|

### 为什么不是分工偏好，而是技术结论

GPUI 的 Windows 后端依赖 DirectX 与 COM，链接走 MSVC —— **从 Linux 交叉编译 Windows 目标不可行**。任何在 Linux 上写的 UI 代码都必须到 Windows 上重新编译验证一次，双端并行只会制造两套未验证状态。加上中文 IME、流畅度、打包安装这三类 T3 验收本来就只有 Windows 是有效环境，把实现也放在 Windows 才能做到"写完即可验"。

### R0 在 130 上的前置（历史，已迁移 Windows）

```bash
rustup update stable          # 当前 1.94.0 → 1.97.1
bash scripts/fetch-pi.sh      # 拉 pi-linux-x64 v0.84.2，验证 --version
```

R0 只产出骨架与脚本，不起窗口，因此**不需要 GPU/Vulkan**。（若日后要在 130 上临时跑一次 demo 窗口，需先 `sudo pacman -S vulkan-intel` —— 当前 `/usr/share/vulkan/icd.d/` 为空，`libvulkan` 装了但驱动 ICD 没装。）

### 编码约定（写进 `CLAUDE.md`，每轮必守）

以 Windows 为第一且唯一目标，**写死平台假设** —— 不再维护 Linux 构建。

| 项 | 约定 |
|---|---|
| 换行 | `.gitattributes` 强制 `* text=auto eol=lf`；Rust 源码一律 LF。判断"文件是否被改过"的哈希必须**忽略换行差异**（pi-web-desktop 踩过这个坑） |
| 路径 | 一律 `std::path::Path`，禁止手拼 `/` 或 `\`；长路径用 `\\?\` 前缀或 `dunce` 规范化 |
| 子进程终止 | 抽象成 `pi_rpc::Process::terminate()`：Windows `taskkill /T /PID`（不能只杀父进程，会留僵尸），非 Windows 走 `kill(-pgid)` |
| 文件替换 | Windows 上**正在被打开的文件不能删/改名** —— 所有原子替换走"写临时文件 + rename"，且 rename 前确保句柄已关 |
| 字体回退 | Windows 用微软雅黑 / Segoe UI，其他平台 Noto Sans CJK SC；字体族列表按平台条件编译，禁止硬编码单一字体 |
| 环境变量 | `HOME` 在 Windows 上是 `USERPROFILE`，统一走 `dirs` crate；`PI_CODING_AGENT_DIR` 必须支持 |
| 测试 fixture | 会话目录名带平台印记（`--C--Users-...` vs `--home-...`），fixture 存归一化后的形式，加载时按平台还原 |

### 协作流程

- 走 **worktree + PR**：分支 `WinClaude/round-NN`；

- 每轮 PR 描述必须贴 validation 输出（T1/T2 的实际命令回显），不贴不审；
